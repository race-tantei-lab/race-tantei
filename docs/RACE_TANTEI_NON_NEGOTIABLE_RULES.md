# レース探偵・絶対条件

最終更新: 2026-08-08

この文書は、ChatGPTの会話履歴が欠落しても参照できるようにGitHubへ恒久保存する。今後の分析・実装・本番反映では、この文書と `config/race-tantei-fixed-constraints.json` を最優先する。

## 1. 購入対象レース数

- 各開催日・各会場で、購入対象を5レース未満にしてはならない。
- 5レースは最低数であり、6レース以上に増やすことは認める。
- 回収率を見かけ上高くする目的で、対象レース数を5未満へ絞ることは禁止する。
- ROI閾値を理由に対象レースを0件または5件未満へ落として完成扱いすることは禁止する。

## 2. コースと購入額

- ライト: 1レース2,000円
- スタンダード: 1レース5,000円
- プレミアム: 1レース10,000円
- 各コースは指定額を使い切る。
- 3コースを同一の買い目構成へ固定する必要はない。各コースの予算に応じて点数・資金配分は変えてよい。
- 買い目点数は固定しない。
- 点数は、各コースの予算・実オッズ・データ漏洩禁止など他の固定条件を守る範囲で、レースやポリシーごとに可変とする。

## 3. 券種と買い目の分散

- 券種はレースごとに可変とする。
- 単勝・ワイド・馬連・馬単・3連複・3連単の6券種から、そのレースで市場歪みルールの根拠が強い券種を選択してよい。
- 毎レースすべての券種を買う必要はない。
- ただし1種類だけの券種へ絞ることは禁止する。各購入対象レースで最低2種類の異なる券種を含める。
- 券種の採否は必ず事前情報・JRA公式オッズ・凍結済みルール/スコアだけで決定する。
- 高配当1点だけへ資金を集中させ、回収率を作ることは禁止する。
- 券種ごとの点数配分と資金配分は固定せず、固定済みポリシーの範囲で可変としてよい。

## 4. オッズ・結果・ルール発見

- 買い目選定に使うオッズは、JRAが公開した実オッズだけとする。
- 単勝オッズから他券種のオッズを作る想定オッズ・推定オッズは禁止する。
- 取得できない過去オッズを後から補完・推測・捏造してはならない。
- 精算はJRAの実際の払戻金だけを使う。
- 固定DBの過去結果・払戻は、**一律ルールのROIを計算し、200%以上の市場歪みを発見・耐久評価するための目的値**として使用してよい。これは本プロジェクトで明示的に採用するルール発見手順である。
- ただし着順・的中・払戻・結果後にしか分からない値をルールの条件式・事前特徴・本番推論へ入れてはならない。
- 特定レースの結果を見て、そのレースだけ条件を追加・削除することは禁止する。発見された条件式は該当する全データへ一律適用する。
- 完成後の本番予測では、当然ながら予測時点で利用可能な情報だけを使う。

## 5. 日付・季節性と耐久性監査

- 日付・季節は多数ある分析要素の一部として補助的に扱う。
- 約2年強のデータしかないため、日付や年を主役にしてモデルを分割したり、特定年月・年×会場などを主要ルールとして期間暗記することは禁止する。
- 主たる分析対象は、馬・騎手・厩舎・近走・速度・着差・コース適性・距離・馬場・頭数・枠・斤量・JRA公式オッズ・市場乖離・券種固有の組合せ構造などとする。
- カレンダー情報を予測特徴として使う場合は補助扱いとし、原則 calendarMonthSin、calendarMonthCos、dayOfYearSin、dayOfYearCos の範囲とする。
- rawの年、日付の通算番号、特定年月を主要な買い条件として使わない。
- 日付だけで買い目や対象レースを決めるルールは禁止する。

### season-balanced 5-slice uniform-rule stability audit

- 最後の数か月だけを唯一の完成判定期間にしない。
- 分割単位はレースではなく開催日 `raceDate` とし、同じ開催日の全会場・全レースを必ず同じsliceへ置く。
- 各 `YYYY-MM` の中で開催日を固定SHA-256順に並べ、slice 0〜4へround-robinで割り当てる。
- これにより春夏秋冬・開催時期が特定sliceへ偏りすぎないようにする。
- この5分割は、**ルールをfoldごとに別々に再学習するためのcrossfitではなく、全固定DBから発見した同一の一律ルール集合が季節バランスの異なる5群すべてで耐えるかを見る耐久性監査**とする。
- slice番号そのものを買い条件に使ってはならない。
- ルールの耐久性スコアを作るために各sliceの過去ROI・最大1件除外ROIを使ってよい。ただし完成ポリシーは全sliceへ完全に同一の条件式・スコア式・レース選択式・券種選択式を適用する。
- レース単位の完全ランダム分割は禁止する。
- 以前に結果を開いた末尾期間や35開催日の監査セットは診断記録であり、「完全未使用」とは扱わない。
- 本番の未来レース予測では、未来結果や同日終了後の結果を予測前に使わない。

## 6. 完成条件とモデル名

- 回収率200%以上は目標ではなく完成条件とする。
- 200%未満の探索物はモデルとして扱わない。
- 探索途中の候補にはバージョン番号を付けない。
- `v16` という名称は、全条件と全ゲートを通過した完成物にだけ付与する。
- 完成判定の全期間回収率は、利用可能な最初のレースから最新の終了済みレースまでを含めて判定する。
- 全期間ROIがライト・スタンダード・プレミアムの全コースで200%以上でなければ完成としない。
- season-balanced 5-slice stability auditの**5sliceすべて**で各コースROI200%以上でなければ完成としない。
- 各stability sliceは各コース100レース以上を必要とする。
- 全期間および各stability sliceで、最大払戻1件を除いたROIが100%以上でなければ昇格しない。
- 最低レース数、最低2券種、固定購入額、公式オッズ限定、結果情報の条件利用禁止、全期間カバレッジの全条件を同時に満たす必要がある。
- 条件を満たすまで完成・成功・v16とは言わない。
- 数値の捏造は禁止する。

## 7. 探索と本番昇格

### 7.1 探索順序の絶対ルール

- 探索は必ず **ルール発見先行** とする。
- 最初に予測モデルや買い目モデルを作り、その出力を過去結果へ当てて「ROIが80%だった」「200%を超えなかった」と結論づける進め方は禁止する。
- まず固定DBに含まれる大量の事前特徴を条件空間として直接分析し、**同じ条件式を全該当データへ一律適用したときにROI200%以上となる市場歪みルールを発見する**。
- 条件空間には、馬・騎手・厩舎・近走・速度・着差・会場・芝ダ・距離帯・頭数・レース番号帯・馬場・天候・公式オッズ帯・市場乖離・券種・券種内順位・各種履歴特徴などを含める。
- 1条件だけでなく、2条件・3条件・4条件・5条件以上の相互作用まで探索対象とする。
- 日付・季節は条件候補の一部として扱ってよいが、短い観測期間を暗記する主軸条件にはしない。
- 200%超ルールを発見した後に初めて、複数ルールを一律の採点式へ統合し、各開催日×会場の最低5レース、最低2券種、各コース固定購入額へ落とし込む。
- したがって、**「予測モデルのROIが80%前後だった」ことを理由に200%ルール探索を終了してはならない。** それはルール探索とは別の診断値にすぎない。

### 7.2 ルールの品質

- 発見したルールは、全体ROIだけでなくサンプル数、最大払戻1件除外後ROI、期間別ROI、期間別最大1件除外後ROIを確認する。
- 一発の巨大払戻だけで200%を作るルールは最上位ルールとして扱わない。
- 同じ馬券・同じレースが複数の200%超ルールに一致する場合、その一致数・ルール強度・耐久性を統合した一律スコアを作ってよい。
- 定数列を条件へ追加して同一ルールを水増ししてはならない。
- 過去データ上で完全に同じ馬券集合へ一致するルールは重複証拠として数えず、同一一致集合につき1本へ重複排除する。
- `PARSE_MISS`、欠損値、不明値、取得失敗そのものを利益シグナルとして利用してはならない。
- ルール集合・採点式・レース選択式・券種選択式は全レースへ同一ロジックで適用する。

### 7.3 本番昇格

- 全ゲート通過後にだけ本番実装・昇格へ進む。
- 200%未満の探索物は内部記録してよいが、本番コード・本番設定・本番買い目へ反映してはならない。
- 不合格結果を逐一ユーザーへ並べて報告しない。
- 全ゲートを通過した探索物だけを昇格処理へ渡し、昇格時に初めて `v16` を付与する。

## 8. 報告と進行

- 作業を始める前に、これから行う内容を説明する。
- 長時間、説明や途中報告なしで黙り込まない。
- ユーザーへ逐一確認を求めず、合意済み条件の範囲で分析を継続する。
- 途中報告は進捗と主要数値に限定し、失敗候補を一つずつ報告しない。
- 全ゲート通過前に完成したと表現しない。
