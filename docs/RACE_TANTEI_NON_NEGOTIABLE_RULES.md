# レース探偵・絶対条件

最終更新: 2026-08-08

この文書は、ChatGPTの会話履歴が欠落しても参照できるようにGitHubへ恒久保存する。今後の分析・実装・本番反映では、この文書と `config/race-tantei-fixed-constraints.json` を最優先する。

## 1. 購入対象レース数

- 各開催日・各会場で、購入対象を5レース未満にしてはならない。
- 5レースは最低数であり、6レース以上に増やすことは認める。
- 回収率を見かけ上高くする目的で、対象レース数を5未満へ絞ることは禁止する。
- ROI閾値を理由に対象レースを0件または5件未満へ落として完成扱いすることは禁止する。

## 2. コースと購入額

- ライト: 1レース2,000円
- スタンダード: 1レース5,000円
- プレミアム: 1レース10,000円
- 各コースは指定額を使い切る。
- 3コースを同一の買い目構成へ固定する必要はない。各コースの予算に応じて点数・資金配分は変えてよい。
- 買い目点数は固定しない。
- 点数は、各コースの予算・実オッズ・データ漏洩禁止など他の固定条件を守る範囲で、レースやポリシーごとに可変とする。

## 3. 券種と買い目の分散

- 券種はレースごとに可変とする。
- 単勝・ワイド・馬連・馬単・3連複・3連単の6券種から、そのレースで期待回収率を下げにくい券種を事前情報だけで選択してよい。
- 毎レースすべての券種を買う必要はない。回収率を大きく悪化させると予測された券種は、そのレースでは外してよい。
- ただし1種類だけの券種へ絞ることは禁止する。各購入対象レースで最低2種類の異なる券種を含める。
- 券種の採否はレース結果を見た後に変更してはならず、必ず事前情報・公式オッズ・固定済みモデル出力だけで決定する。
- 高配当1点だけへ資金を集中させ、回収率を作ることは禁止する。
- 券種ごとの点数配分と資金配分は固定せず、モデル出力に応じて可変としてよい。

## 4. オッズと検証データ

- 買い目選定に使うオッズは、JRAが公開した実オッズだけとする。
- 単勝オッズから他券種のオッズを計算する処理、想定オッズ、推定オッズは禁止する。
- 取得できない過去オッズを後から補完・推測・捏造してはならない。
- 精算はJRAの実際の払戻金だけを使う。
- 結果、着順、払戻金を見た後に条件を決める後付け最適化は禁止する。

## 5. 日付・季節性と検証設計

- 日付・季節は多数ある分析要素の一部として補助的に扱う。
- 約2年強のデータしかないため、日付や年を主役にしてモデルを分割したり、特定年月・年×会場などを主要ルールとして期間暗記することは禁止する。
- モデルの主たる分析対象は、馬・騎手・厩舎・近走・速度・着差・コース適性・距離・馬場・頭数・枠・斤量・公式オッズ・市場乖離・券種固有の組合せ構造などとする。
- カレンダー情報は補助特徴として、原則 calendarMonthSin、calendarMonthCos、dayOfYearSin、dayOfYearCos の4特徴だけを使う。
- rawの年、日付の通算番号、特定年月をそのまま主要特徴として使わない。
- 日付だけで買い目や対象レースを決めるルールは禁止する。

### season-balanced 5-fold crossfit

- 検証では最後の数か月だけをホールドする方式を使わない。
- 分割単位はレースではなく開催日 `raceDate` とし、同じ開催日の全会場・全レースを必ず同じfoldへ置く。
- 各 `YYYY-MM` の中で開催日を固定SHA-256順に並べ、fold 0〜4へround-robinで割り当てる。
- これにより各foldへ季節・開催時期が偏りすぎないようにする。
- 各開催日は必ず1回だけout-of-foldで評価する。
- その開催日を評価するfoldの学習には、そのfoldの結果を使わない。
- レース単位の完全ランダム分割は禁止する。
- 以前に結果を開いた末尾期間や35開催日の監査セットは、今後は診断記録であり「完全未使用」とは扱わない。
- 本番の未来レース予測では、当然ながら予測時点までに利用可能な情報だけを使い、未来結果や同日終了後の結果を予測前に使わない。

## 6. 完成条件とモデル名

- 回収率200%以上は目標ではなく完成条件とする。
- 200%未満の探索物はモデルとして扱わない。
- 探索途中の候補にはバージョン番号を付けない。
- `v16` という名称は、全条件と全ゲートを通過した完成物にだけ付与する。
- 完成判定の全期間回収率は、利用可能な最初のレースから最新の終了済みレースまでを含めて判定する。
- 全期間回収率とseason-balanced 5-fold crossfitのout-of-fold回収率の両方で、ライト・スタンダード・プレミアムの全コースが200%以上でなければ完成としない。
- crossfit評価は各コース100レース以上を必要とする。
- 最大払戻1件を除いた回収率が各コース100%以上でなければ昇格しない。
- 最低レース数、最低2券種、固定購入額、公式オッズ限定、データ漏洩禁止、全期間カバレッジの全条件を同時に満たす必要がある。
- 条件を満たす候補が見つかるまで、完成・成功・v16とは言わない。
- 数値の捏造、結果からの逆算は禁止する。

## 7. 探索と本番昇格

### 7.1 探索順序の絶対ルール

- 探索は必ず **ルール発見先行** とする。
- 最初に予測モデルや買い目モデルを作り、その出力を過去結果へ当てて「ROIが80%だった」「200%を超えなかった」と結論づける進め方は禁止する。
- まず固定DBに含まれる大量の事前特徴を条件空間として直接分析し、**同じ条件式を全該当データへ一律適用したときにROI200%以上となる市場歪みルールを発見する**。
- 条件空間には、馬・騎手・厩舎・近走・速度・着差・会場・芝ダ・距離帯・頭数・レース番号帯・馬場・天候・公式オッズ帯・市場乖離・券種・券種内順位・各種履歴特徴などを含める。
- 1条件だけでなく、2条件・3条件・4条件・5条件以上の相互作用まで探索対象とする。
- 日付・季節は条件候補の一部として扱ってよいが、短い観測期間を暗記する主軸条件にはしない。
- 200%超ルールを発見した後に初めて、複数ルールを一律の採点式へ統合し、各開催日×会場の最低5レース、最低2券種、各コース固定購入額へ落とし込む。
- したがって、**「予測モデルのROIが80%前後だった」ことを理由に200%ルール探索を終了してはならない。** それはルール探索とは別の診断値にすぎない。

### 7.2 ルールの品質

- 発見したルールは、全体ROIだけでなくサンプル数、最大払戻1件除外後ROI、期間別ROI、期間別最大1件除外後ROIを確認する。
- 一発の巨大払戻だけで200%を作るルールは最上位ルールとして扱わない。
- 同じ馬券・同じレースが複数の200%超ルールに一致する場合、その一致数・ルール強度・耐久性を統合した一律スコアを作ってよい。
- ルール集合・採点式・レース選択式・券種選択式は全レースへ同一ロジックで適用する。

### 7.3 本番昇格

- 固定DBを先に分析し、回収率200%以上を生む再現可能な市場の歪みを発見して一般化する。
- 買い方パターンの総当たりをモデル探索の中心に置かない。
- 200%未満の探索物は内部記録してよいが、本番コード・本番設定・本番買い目へ反映してはならない。
- 不合格結果を逐一ユーザーへ並べて報告しない。
- 全ゲートを通過した探索物だけを昇格処理へ渡し、昇格時に初めて `v16` を付与する。

## 8. 報告と進行

- 作業を始める前に、これから行う内容を説明する。
- 長時間、説明や途中報告なしで黙り込まない。
- ユーザーへ逐一確認を求めず、合意済み条件の範囲で分析を継続する。
- 途中報告は進捗と主要数値に限定し、失敗候補を一つずつ報告しない。
- 全ゲート通過前に完成したと表現しない。
